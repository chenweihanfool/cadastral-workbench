# 真接圖（true seam-join）原型腳本

這個資料夾保存的是「真正接圖」邏輯的一次性原型腳本，**尚未整合進
`python/join_cadastral.py` / 網頁版接圖模組**，純粹作為之後正式整合時的
參考實作與已驗證過的演算法記錄。腳本裡的路徑（`sheets.pkl`、
`/root/.claude/uploads/...`）是當時工作階段的暫存路徑，不能直接執行，
需要的是裡面的邏輯，不是照抄檔案路徑。

## 背景

既有的接圖模組（v1，`python/join_cadastral.py`）只是把多個分幅的
COA/BNP/PAR **單純拼接**在一起：座標點全域重新編號、(段,小段) 鍵撞號時
用 `SUB_OFFSET` 錯開，但完全不處理分幅接縫。這會留下一個視覺上很明顯
的問題：跨分幅的同一筆真實地號，因為在紙圖數化時各分幅只畫得到自己
框線以內的部分，兩個分幅都會各自畫一條「假的框線收邊」，拼接後在接縫
處看起來是兩條平行/垂直的雙線，而不是一條連續的地籍線。

## 真接圖的演算法

1. **判斷分幅相鄰關係**：用每個分幅的 bbox，找出上下（h）或左右（v）
   相鄰、且共邊長度夠長（排除只共角的對角分幅）的分幅配對，算出雙方
   接觸的框線位置。
2. **找出跨分幅共用的 (段,小段) 鍵**：同一把鍵出現在兩個以上分幅，且
   這些分幅彼此透過上一步的相鄰關係可以連通，代表是同一筆被接縫切開
   的真實地號（**這個假設只在本專案的資料慣例下成立**——這批 KC 格式
   資料裡，跨分幅出現同一組 (段,小段) 代表就是同一筆地號的延續；這跟
   `join_cadastral.py` docstring 裡「不同分幅數字相同的鍵視為不同地號」
   的既有假設是相反的，兩種資料來源要分開處理，不能混用同一套邏輯）。
3. **刪除接圖線上的假界址點、直接相連**：對每個相鄰分幅配對，各自用
   **自己分幅的框線位置**（不是兩分幅框線的平均值——兩個分幅的框線
   實際上有幾公分到幾公尺的未校正微差）去判斷哪些界址點緊貼框線，抓出
   單一連續的那一段假點（用小容許誤差，例如 1.5 m，太大會誤刪真實的
   地號轉角）。把這段假點從環狀點列中裁掉，剩下兩段各自的「開放鏈」，
   直接首尾相接成一條連續的多邊形，不做任何幾何切割或平均。
4. **邊界情況**：
   - 整段都落在框線上（沒有任何真實界址點留下）→ 該側視為空，直接用
     另一側的鏈當作最終結果（等於單側直接封閉）。
   - 單一分幅內同一把鍵本身就有重複點號（代表它本來就不是簡單多邊形，
     例如自我相切的複雜形狀）→ 不強行拼接，維持原樣分開輸出，避免拼出
     自我相交的錯誤形狀。
   - 一把鍵同時出現在 3 個以上分幅（例如四個分幅的交角）→ 用 union-find
     取一個生成樹的相鄰邊順序逐步合併，而不是每一組相鄰邊都各自獨立處理
     一次（否則同一組假點會被重複處理）。
5. **驗證**：用 shapely 檢查合併後多邊形是否 valid（無自我相交），並用
   shoelace 面積跟 PAR 的登記面積（`area_reg`，接圖前後應該相同，因為是
   地政登記的法定面積）/計算面積（`area_calc`，注意這個欄位在原始資料
   裡是**每個分幅片段各自的面積**，不是整筆地號的面積，比對時要把同一
   把鍵所有片段的 `area_calc` 加總才是正確的比較基準）交叉比對。

## 檔案

- `common.py` — 共用的 COA/BNP/PAR 解析函式（跟 `python/join_cadastral.py`
  的 `_parse_coa` / `_parse_bnp` / `_parse_par` 邏輯一致，欄寬已用真實資料
  逐位元組驗證過，見該檔案 docstring）。
- `analyze.py` — 分析跨分幅共用鍵的分佈（2 分幅 / 3 分幅 / 4 分幅以上），
  確認相鄰關係跟共用鍵是否一致。
- `splice.py` — 核心真接圖演算法（上述步驟 1–4），輸出 `merged_parcels`
  （每筆地號的最終環狀點列、是否成功接圖、涉及哪些分幅）。
- `validate.py` — 面積 / 幾何有效性交叉驗證。
- `export_final.py` — 把 `splice.py` 的結果匯出成 COA/BNP/PAR（沿用
  `join_cadastral.py` export 模式驗證過的固定欄寬格式）。
- `clip_after_join.py` / `export_clipped.py` — 真接圖完成「之後」再依另一
  份參考範圍資料（例如 KC6336）整體聯集範圍篩選，整筆保留不切割，最後
  才重新編號輸出。

## 重要：跟既有「切範圍」一次性任務的執行順序

分幅 → 真接圖（同時完成拼接與去接圖假線）→ 切範圍。

切範圍（依某個參考範圍篩選地號）一定要放在真接圖**之後**執行。切範圍
或任何全域重新編號的動作，都會把「這個點/這把鍵原本屬於哪個分幅」的
資訊攤平抹掉，之後就無法再用分幅框線位置判斷哪些界址點是接圖線上的
假點了。如果先切範圍、再想做真接圖，會缺少分幅身分資訊，只能退化成
純幾何方式重新猜測接縫（沒有做過，可行性未知，優先順序應該是避免
發生這種情況，而不是另外實作一套幾何猜測法）。

## 整合進 APP 時要考慮的地方

- 目前的「相鄰分幅判斷」跟「跨分幅共用鍵代表同一地號」都是**假設**，
  只在這批 KC 格式測試資料上驗證過；正式整合時應該讓使用者能選擇要用
  哪一種語意（v1 的「同鍵視為不同地號」vs. 這裡的「相鄰分幅同鍵視為
  同一地號」），或是想辦法從資料自動判斷（例如比對兩側面積總和是否
  接近登記面積）。
- 目前的容許誤差（相鄰判斷 5 m、接圖假點判斷 1.5 m）是針對這批測試
  資料人工調校出來的，換一批分幅框線精度不同的資料可能需要重新調整，
  或做成可調參數。
- 目前對「單一分幅內同一把鍵本身有重複點號」「一把鍵橫跨 3 個以上不
  相連的分幅群組」這幾種複雜情況都是保守跳過、維持原樣，沒有強行處理；
  正式整合時應該把這些情況清楚列在使用者看得到的報告裡（類似現有
  `seam_report` 的呈現方式），而不是靜默跳過。
